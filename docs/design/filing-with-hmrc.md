# Design: full CT600 filing with HMRC

Status: agreed 2026-09-29. Scope: iXBRL accounts and computations, real HMRC submission (Government
Gateway / Transaction Engine), group relief, R&D relief, and supplementary pages CT600A–CT600P.
Research and official material: `specs/` (start with `specs/research/*.md`).

## Decisions

| Decision | Why |
| --- | --- |
| Target CT600 schema **v1.994** (`specs/hmrc/ct600-v1.994/`) | Live in HMRC's services today; v1.995 is published but "awaiting implementation". |
| **Schema-driven** supplementary pages and XML | 15 pages and ~1,300 boxes. Generating the element tree from HMRC's XSD + box map gives uniform, schema-valid forms and XML; hand-written code is reserved for calculations. |
| Validate every generated return **offline** against the XSD **and HMRC's schematron** (1,072 business rules) | The same checks HMRC runs, available without credentials, so users see HMRC's own error messages before submitting. |
| iXBRL accounts on the **FRC 2026** taxonomy; computations on **HMRC ct-comp 2024** | FRC 2026 is accepted with no end date. ct-comp 2025 is not published: returns for periods ending after 31 March 2026 cannot carry accepted computations yet (HMRC error 3320). The service says so plainly and blocks live submission for those periods rather than send something HMRC will reject. |
| Validate iXBRL with **Arelle** offline in tests | Only open-source validator that checks the FRC/HMRC rules; taxonomy packages pinned by SHA-256 in `specs/ixbrl/taxonomies.tsv`. |
| Submit via the **Transaction Engine** with the company's **Government Gateway** user ID and password, supplied per submission and never stored or logged | The only CT600 channel HMRC offers. `Method=clear` is the only supported authentication. |
| Environments: `live`, `test-in-live` (TIL, class `HMRC-CT-CT600-TIL`), `ets` (HMRC test service, SDST test credentials), `tpvs` (third-party validation service, no credentials, synthetic data only) | TIL is HMRC's route for testing with real data; TPVS lets CI prove the whole message (schema, rules, IRmark, iXBRL) is accepted by HMRC. |
| Vendor ID from configuration (`HMRC_VENDOR_ID`); live and TIL submission are disabled with an explicit message when it is unset | HMRC allocates it to recognised software developers (SDSTeam@hmrc.gov.uk). This project cannot obtain one on its own. |
| Real submissions require both the vendor ID and the operator enabling them (`HMRC_SUBMISSION_ENABLED=true`) | A public demo deployment must not relay Gateway passwords by default. |

## Backend modules and ownership

```
backend/src/open_ct600/
  ct600.py            # input model + computation (CORE lane)
  reliefs/            # group_relief.py, research_and_development.py, loans_to_participators.py (CORE)
  pages/              # supplementary page linkage: computed boxes + main-return effects (CORE)
  schema/             # generate.py (XSD + box map → spec), spec.py (loader), ct600-v1.994.json (CORE)
  ixbrl/              # accounts.py, computations.py, xhtml.py (IXBRL lane)
  hmrc/               # xml.py, irmark.py, govtalk.py, client.py, validate.py (HMRC lane)
  main.py             # routes: each lane adds its own endpoints
```

### Schema spec (CORE) — `schema/ct600-v1.994.json`

Generated by `python -m open_ct600.schema.generate` from the XSD and `specs/hmrc/box-map-v1.995.tsv`, committed,
and checked in CI to be up to date. One node per element/attribute:

```json
{"name": "LoansByCloseCompanies", "path": "/IRenvelope/CompanyTaxReturn/LoansByCloseCompanies",
 "box": "A5", "label": "…", "kind": "group|money|pounds|pence|integer|decimal|percent|date|yes|yesno|text|enum",
 "min": 0, "max": 1 | null, "choice": "group-id or null", "enum": [...], "pattern": "...",
 "minLength": 2, "maxLength": 56, "minValue": ..., "maxValue": ..., "children": [...]}
```

`spec.pages()` returns the 15 page roots (A..P, including dormant G) with their codes and titles.

### Input model (CORE) — additions to `CT600Return`

```python
company: CompanyDetails            # + company_type: int (0–11, default 0), principal_activity: str
accounts: AccountsDetails          # standard: "micro" | "small"; approval_date; directors: list[str] (≥1);
                                   # signing_director (one of directors); average_employees; trading_status
balance_sheet: BalanceSheet        # + called_up_share_capital_not_paid, prepayments_and_accrued_income,
                                   #   provisions, accruals_and_deferred_income
supplementary_pages: SupplementaryPages   # page code → element tree (JSON mirroring the XSD, element names
                                          # as keys, lists for repeating elements), validated against the spec
```

R&D, group relief and loans to participators are entered **on their pages** (L, C, A). Boxes the service
calculates (totals, tax at rates, credits) are marked `computed` in the page definitions and are not
user-entered; `pages/` fills them in.

### Computation (CORE) — `ReturnComputation`

Existing fields plus:

```python
boxes: tuple[CT600Box, ...]        # box id is now a string: "145", "A80", "C10", "L210", …
pages: dict[str, dict]             # completed page trees (user answers + computed boxes)
reliefs: ReliefsSummary            # group relief used, R&D deduction/credit/payable credit, s455 tax
```

Set-off order and linkages follow the form and schema (not the guide where they conflict): 300 → 305 → 310
→ 312 → 315; A80 → 480; C10 → 310; C130 → 312; L210 → 530; L180 → 875; L125 → 880; N285 → 497; I70 → 505.

### iXBRL (IXBRL lane) — `ixbrl/`

```python
render_accounts(ct600: CT600Return, computation: ReturnComputation) -> str        # XHTML, FRC 2026
render_computations(ct600: CT600Return, computation: ReturnComputation) -> str    # XHTML, ct-comp 2024
```

Human-readable documents (they are the company's statutory accounts and computations), fully tagged, no
script, CSS embedded, only XML entities. Tests validate both with Arelle offline (`--calc=xbrl21`, UK
plugin, `hmrc` disclosure system for accounts) and fail on any warning.

### HMRC (HMRC lane) — `hmrc/`

```python
build_return_xml(ct600, computation, accounts_xhtml, computations_xhtml) -> lxml IRenvelope
validate_return(envelope) -> list[Problem]          # XSD + schematron; Problem = code, message, box, path
add_irmark(govtalk_message) -> str                  # C14N 1.0 of Body minus IRmark, SHA-1, Base64
build_govtalk(body, environment, credentials, vendor) -> bytes
TransactionEngineClient.submit(message) -> Receipt | BusinessErrors   # submit → poll → delete
```

API: `POST /api/returns/validate` (XML + schematron problems mapped to boxes and pages),
`GET /api/returns/xml|accounts|computations` equivalents as `POST` with the return body (downloads), and
`POST /api/returns/submit-to-hmrc` taking `{ct600, declaration, environment, gateway_user_id,
gateway_password}`. The demo receipt endpoint stays for deployments without a vendor ID.

### Frontend (FRONTEND lane)

- New task list sections: accounts details (standard, directors, approval date, employees, activity),
  extended balance sheet, and "Supplementary pages" — choose pages that apply, then a generic
  GOV.UK form per page rendered from the schema spec (`GET /api/schema/pages`), with repeating tables.
- Check your answers: HMRC validation problems (from `/api/returns/validate`) listed in an error
  summary that links to the page and field; downloads for the iXBRL accounts, computations and CT600 XML.
- Declaration: choose Test in Live or live; Government Gateway user ID and password inputs
  (`autocomplete="off"`, never persisted); HMRC's receipt (IRmark, correlation ID, accepted time) on the
  confirmation page.

## Verification (definition of done)

1. HMRC's IRmark worked example reproduced byte-for-byte.
2. Every generated return validates against the XSD and schematron with no errors (property-style
   tests over representative returns: dormant, trading micro, small with group relief, R&D merged scheme,
   ERIS, pre-April-2024 SME, s455 loans, each supplementary page).
3. Generated iXBRL passes Arelle offline with zero warnings.
4. A synthetic return with iXBRL accounts and computations submitted to **TPVS** returns a signed success
   receipt whose digest equals our IRmark (opt-in test, `-m hmrc_tpvs`).
5. The Transaction Engine client's submit → poll → delete flow and every error class are tested against a
   stub TE that replays HMRC's documented messages.
6. Frontend: journeys for each new section, generic page forms, validation errors, and submission.
